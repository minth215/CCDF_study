Set 1 · Q1

A support agent should remember a customer's communication preference across separate sessions without retaining raw transcripts. Every autonomous step must remain inspectable and subject to the required operational controls. What design best fits?

지원(support) 에이전트가 원본 대화 기록(raw transcript)을 보관하지 않으면서, 서로 분리된 세션들에 걸쳐 고객의 커뮤니케이션 선호도를 기억해야 합니다. 또한 모든 자율적 단계는 검사 가능(inspectable)해야 하며 요구되는 운영 통제를 받아야 합니다. 어떤 설계가 가장 적합한가요?

  1. Store the validated preference in customer-scoped memory, and begin each support session with a fresh conversational context. The application would follow this approach to remember preferences without retaining raw transcripts.

    검증된 선호도를 고객 단위(customer-scoped) 메모리에 저장하고, 각 지원 세션은 새로운 대화 컨텍스트로 시작한다. 애플리케이션은 이 방식을 따라 원본 대화 기록을 보관하지 않고도 선호도를 기억하게 된다.

  2. Expect Claude to recall earlier sessions without attaching saved memory or resupplying relevant prior state. Reviewers would evaluate whether this can remember preferences without retaining raw transcripts.

    저장된 메모리를 첨부하거나 관련 이전 상태를 다시 제공하지 않은 채, Claude가 이전 세션을 알아서 기억할 것이라고 기대한다. 검토자는 이 방법으로 원본 대화 기록 없이 선호도를 기억할 수 있는지 평가하게 된다.

  3. Replay full transcripts in every session, retaining unrelated customer details merely to recover one communication preference. The application would follow this approach to remember preferences without retaining raw transcripts.

    매 세션마다 전체 대화 기록을 다시 불러오며, 단 하나의 커뮤니케이션 선호도를 복원하기 위해 관련 없는 고객 정보까지 계속 보관한다. 애플리케이션은 이 방식을 따라 원본 대화 기록을 보관하지 않고 선호도를 기억하게 된다.

  4. Place every customer's preferences in one shared memory record available to all support sessions. The design would use this reasoning to remember preferences without retaining raw transcripts.

    모든 고객의 선호도를 모든 지원 세션에서 접근 가능한 하나의 공유 메모리 레코드에 담아 둔다. 이 설계는 그러한 논리로 원본 대화 기록 없이 선호도를 기억하려 한다.

정답: 1번 (초록색 표시)핵심 요구사항은 세 가지입니다. ① 세션 간 정보 유지, ② 원본 대화 기록 미보관, ③ 각 단계의 검사 가능성. 정답인 이유: 원본 대화 전체가 아니라 검증된 선호도라는 결과값만 저장하므로 ②를 만족합니다. 저장 범위를 고객 단위로 한정해 고객 간 데이터가 섞이지 않고, 세션마다 새 컨텍스트로 시작하면 이전 세션의 잔여 상태가 몰래 흘러들지 않아 "지금 이 세션에 무엇이 들어갔는지"가 명확해집니다 — 이것이 ③의 검사 가능성입니다. 오답 이유 • Claude가 알아서 기억할 것이라 기대 — 모델은 세션 간 상태를 자동으로 보존하지 않습니다. 필요한 상태는 애플리케이션이 명시적으로 다시 제공해야 합니다. • 전체 기록 재생 — ②를 정면으로 위반하고, 불필요한 개인정보까지 최소 수집 원칙에 어긋나게 보관합니다. • 하나의 공유 메모리 레코드 — 고객 간 데이터 격리가 깨져 A 고객의 정보가 B 고객 세션에 노출될 수 있는 심각한 설계 결함입니다. 기억할 원칙: 세션 간 지속성은 "원본을 쌓아두기"가 아니라 "필요한 결론만 범위를 좁혀 저장하기"로 푼다.
Set 1 · Q2틀린 문제

Claude returns schema-conforming JSON for a production configuration update. Before applying the change, what should the application do next? Any revision must be evaluated against the same quality and latency criteria before release.

Claude가 운영 환경(production)의 설정 변경을 위해 스키마를 준수하는 JSON을 반환했습니다. 변경을 적용하기 전에 애플리케이션이 다음으로 해야 할 일은 무엇인가요? 모든 수정 사항은 배포 전에 동일한 품질 및 지연 시간 기준으로 평가되어야 합니다.

  1. Skip semantic validation whenever all required property names appear in the expected order. The application would follow this approach to validate authorization and business rules before execution.

    필수 속성 이름이 모두 예상한 순서대로 나타나기만 하면 의미적 검증(semantic validation)을 건너뛴다. 애플리케이션은 이 방식을 따라 실행 전에 권한과 비즈니스 규칙을 검증하게 된다.

  2. Check completion status, validate rules and facts, then authorize the downstream action. This would become the basis used to validate authorization and business rules before execution.

    완료 상태를 확인하고, 규칙과 사실관계를 검증한 다음, 후속 동작(downstream action)을 승인한다. 이것이 실행 전에 권한과 비즈니스 규칙을 검증하는 기준이 된다.

  3. Convert the JSON into prose and trust whichever explanation sounds most confident to an operator. The team would then validate authorization and business rules before execution based on that assumption.

    JSON을 산문(prose)으로 변환한 뒤, 운영자에게 가장 확신에 차 보이는 설명을 신뢰한다. 팀은 그 가정에 근거해 실행 전에 권한과 비즈니스 규칙을 검증하게 된다.

  4. Apply the configuration immediately because strict schema conformance guarantees every target fact and instruction is correct. The design would use this reasoning to validate authorization and business rules before execution before release.

    엄격한 스키마 준수가 모든 대상 사실과 지시가 올바름을 보장하므로 설정을 즉시 적용한다. 이 설계는 그러한 논리로 배포 전 실행 전에 권한과 비즈니스 규칙을 검증하려 한다.

정답: 2번 (초록색 표시)핵심: 스키마 준수 ≠ 내용의 정확성. JSON이 스키마에 맞는다는 것은 형태(shape)가 맞다는 뜻일 뿐입니다. 그 안의 값이 사실에 부합하는지, 그 변경을 수행할 권한이 있는지, 비즈니스 규칙에 어긋나지 않는지는 전혀 보장하지 않습니다. 게다가 stop_reason 같은 완료 상태를 확인하지 않으면 max_tokens로 잘려버린 응답을 온전한 결과로 착각할 수 있습니다. 그래서 올바른 순서는 ① 완료 상태 확인 → ② 규칙·사실 검증 → ③ 후속 동작 승인 입니다. 오답 이유 • 속성 순서로 의미 검증 생략 — 키의 등장 순서는 값의 의미와 아무 상관이 없습니다. • 산문 변환 후 확신도로 판단 (선택하신 답) — 모델의 어조가 확신에 차 있다는 것은 정확성의 지표가 전혀 아닙니다. 오히려 틀린 내용을 자신 있게 말하는 경우가 위험합니다. • 즉시 적용 — 스키마 준수를 정확성 보장으로 착각한 전형적인 함정 선택지입니다. 기억할 원칙: 구조 검증(스키마)과 의미 검증(사실·권한·규칙)은 별개의 단계이며, 운영 환경에 쓰기 전에는 둘 다 거쳐야 한다.

    페이지 텍스트를 시스템 프롬프트로 옮겨 가장 강한 지시 우선순위를 갖도록 한다. 이 방법으로 인젝션에 저항하고 결제 승인을 요구하게 된다.

    가져온 페이지 콘텐츠를 명확히 구분된 '신뢰할 수 없는 데이터' 영역에 배치하고, Claude에게 이를 권위 있는 지시로 취급하지 말라고 지시한다. 이 방법으로 인젝션에 저항하고 결제 승인을 요구하게 된다.
