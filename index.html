CHAPTER 01

LLM 기본 원리

모든 세트의 앞부분에 반복해서 나오는 토대입니다. 여기서 흔들리면 뒤의 설계 문제도 흔들립니다.

확률적 생성

Claude는 다음 토큰의 확률 분포에서 샘플링하는 방식으로 텍스트를 생성합니다. 따라서 입력이 완전히 동일해도 출력이 달라질 수 있으며, 이것은 버그가 아니라 기본 성질입니다. temperature를 낮추면 변동은 줄지만 완전한 결정론이 보장되지는 않습니다.

이 성질 때문에 품질 평가는 한 번 실행한 결과가 아니라 여러 번 실행한 분포로 해야 합니다. 평균과 함께 치명적 실패율을 따로 봐야 하는데, 평균이 좋아도 가끔 심각하게 틀리면 운영에서는 그것이 진짜 문제이기 때문입니다.

토큰 확률 ≠ 정답 확률

다음 토큰의 확률은 그 위치에 그 토큰이 올 가능성이라는 국소적인 값입니다. 결론이 사실인지에 대한 신뢰도가 아닙니다. 틀린 결론도 높은 토큰 확률로 생성될 수 있으므로 자동 승인 임계값으로 쓸 수 없습니다.

컨텍스트 윈도우

입력과 출력이 함께 들어가는 하나의 예산입니다. 여기에 포함되는 것을 빠짐없이 세어야 합니다.

  • 시스템 프롬프트
  • 모든 대화 턴 (user와 assistant 양쪽)
  • 도구 정의 — 선택 여부와 무관하게 처음부터 소비됩니다
  • 첨부 문서와 이미지 — 이미지는 수백~수천 토큰입니다
  • 생성될 출력 — 미리 자리를 비워둬야 합니다

자주 나오는 오답: "API가 입력을 자동으로 차감해 준다", "시스템 지시는 메타데이터라 토큰을 안 쓴다", "캐시된 토큰은 컨텍스트를 차지하지 않는다" — 전부 틀렸습니다.

토큰 수 세기

문자 수를 4로 나누는 어림값은 영어 산문에서나 대충 맞고, 코드·URL·한국어·이모지에서는 크게 빗나갑니다. 중요한 판단에 쓰려면 토큰 계산 엔드포인트에 실제 메시지 구조를 담아 호출하고, 사후에는 응답의 usage 필드로 대조합니다.

CHAPTER 02

Messages API 기초

형식을 묻는 문제는 배점이 확실합니다. 헷갈리는 지점이 정해져 있으니 그것만 확실히 외워두면 됩니다.

요청 구조

messages 배열에 들어갈 수 있는 역할은 user와 assistant 뿐입니다. 시스템 지시는 배열 안의 role: "system" 메시지가 아니라 요청 본문의 최상위 system 파라미터입니다.

{
  "system": "지속적인 역할과 규칙",
  "messages": [
    {"role": "user", "content": "작업별 콘텐츠"}
  ]
}

다른 API에 익숙한 개발자가 가장 자주 틀리는 지점이라 시험에도 반복해서 나옵니다.

무상태(stateless)

Messages API는 대화를 저장하지 않습니다. 서버 측 대화 메모리도, API 키에 연결된 이전 대화도 없습니다. 대화 상태 관리는 전적으로 애플리케이션의 책임이며, 매 요청마다 대화 전체를 다시 보내야 합니다.

따라서 세션 간 기억이 필요하면 애플리케이션이 영속 저장하고, 무상태 컨테이너 환경이라면 공유 외부 저장소에 두어야 어느 컨테이너가 요청을 받든 재개할 수 있습니다.

stop_reason 먼저 확인

응답을 쓰기 전에 반드시 stop_reason부터 봅니다.

  • end_turn — 정상 완료
  • max_tokens — 출력 한도에 걸려 잘림. 완결된 답이 아니므로 하위 시스템에 넘기면 안 됩니다
  • tool_use — 도구 실행 요청
  • refusal — 안전상 거부. 비즈니스 스키마 JSON이 아예 없으므로 파싱 대상이 아닙니다
  • pause_turn — 서버 도구 루프가 일시 정지. 받은 콘텐츠를 붙여서 후속 요청으로 이어갑니다

응답 콘텐츠는 블록 배열

response.content는 배열이며 content[0]이 항상 텍스트라는 보장이 없습니다. 배열을 순회하며 block.type으로 분기해야 합니다. TypeScript라면 판별 유니온과 never 검사로 새 블록 타입 누락을 컴파일 타임에 잡을 수 있습니다.

원시 REST 호출

SDK를 쓰지 않고 직접 호출한다면 헤더 세 개가 필수입니다.

  • x-api-key — 인증
  • anthropic-version — 가장 자주 빠뜨리는 헤더
  • content-type: application/json

SDK는 같은 API를 감싸는 편의 계층입니다. 프롬프트를 고치거나 모델을 바꾸지 않으므로, 동등한 요청이면 동작도 동일합니다.

CHAPTER 03

도구 사용 (Tool Use)

네 세트 모두에서 가장 많이 출제된 영역입니다. 루프의 형식과 스키마 설계 두 갈래로 나옵니다.

도구 루프의 형식

순서와 역할을 정확히 외워야 합니다.

  1. Claude가 stop_reason: "tool_use"와 함께 assistant의 tool_use 블록을 반환
  2. 애플리케이션이 인자를 검증하고 도구를 실행 (모델이 실행하지 않습니다)
  3. 결과를 user 역할의 tool_result 블록으로 반환. tool_use_id는 원래 호출과 정확히 일치
  4. 대화 전체를 다시 보내 다음 응답을 받음

반드시 지켜야 할 세 규칙: ① tool_result는 user 메시지의 맨 앞에 온다 (텍스트를 붙이려면 그 뒤에) ② 요청된 모든 tool_use에 결과를 돌려준다 (실패는 is_error로 표시) ③ assistant의 tool_use 블록도 대화에 포함해서 다시 보낸다

여러 도구를 한 턴에 요청받았다면 하나의 user 메시지에 모든 tool_result를 담습니다. 독립적인 읽기 전용 도구는 병렬 실행해도 되지만, 순서 의존성이나 부수 효과가 있는 도구는 병렬 그룹에서 제외합니다.

스키마 설계

properties에 선언하는 것과 필수로 만드는 것은 별개입니다. 반드시 있어야 하면 required 배열에 명시합니다.

  • 값의 범위 → type: "integer" + minimum
  • 허용된 값 집합 → enum
  • 스키마가 표현하지 못하는 것 → 파싱 후 코드 검증

스키마는 실행기가 실제로 요구하는 것을 그대로 표현해야 합니다. 계약이 어긋나면 모델이 유효한 호출을 만들어도 실행기가 실패합니다.

설명(description)에 "이렇게 해주세요"라고 쓰는 것은 힌트일 뿐 강제가 아닙니다. 강제하려면 스키마 구조로 표현하거나 코드에서 검증해야 합니다.

도구 정의는 모델을 위한 문서

이름이 lookup, lookup2이고 설명이 같으면 모델이 구별할 근거가 없습니다. 동작 중심의 구별되는 이름, 언제 쓰는지에 대한 설명, 실행기와 일치하는 정확한 인자 세 가지를 갖춰야 합니다.

도구가 아주 많을 때

수백~수천 개의 도구를 매 요청에 전부 보내면 입력 비용이 커지고 선택 신뢰성도 떨어집니다. 도구 검색 / 지연 로딩으로 관련 있는 부분집합만 런타임에 로드하되, 각 도구의 스키마와 권한 확인은 그대로 유지합니다.

함정 선택지: "자유 형식 이름과 임의 JSON을 받는 범용 execute_tool" — 비용은 줄지만 검증과 권한 통제가 사라지는 심각한 보안 결함입니다.

CHAPTER 04

스트리밍

전송 방식에 대한 오해를 묻는 문제가 반복됩니다. SSE라는 것만 확실히 알면 대부분 풀립니다.

HTTP 위의 SSE

Claude 스트리밍은 Server-Sent Events 방식입니다. 하나의 HTTP 응답을 열어둔 채 이벤트를 순차적으로 흘려보냅니다. WebSocket이 아니며 필요하지도 않습니다. 서버 → 클라이언트 단방향이므로 SSE가 더 단순하고, 기존 HTTP 인프라(프록시·로드밸런서·인증)를 그대로 쓸 수 있습니다.

오답 패턴: "HTTP는 완결된 JSON 하나만 반환할 수 있다", "이벤트마다 별도 요청이 발생한다", "스트리밍 이벤트가 서버 리소스로 저장되니 폴링해야 한다" — 전부 사실이 아닙니다.

델타는 조각이다

partial_json이나 text_delta는 이름 그대로 부분입니다. {"city":"San 같은 조각은 유효한 JSON이 아니므로 개별 파싱하면 실패합니다. 순서대로 이어 붙였다가 콘텐츠 블록이 끝난 뒤 한 번에 파싱하거나, SDK의 누적 헬퍼를 씁니다.

표시와 저장을 분리

스트리밍 처리의 핵심 원칙입니다.

  • 표시 — 델타가 도착할 때마다 즉시 화면에. 단 잠정으로 취급합니다
  • 저장 — 스트림이 성공적으로 완료된 뒤 한 번만 완결된 메시지를 저장

HTTP 200은 연결이 성립했다는 뜻일 뿐입니다. 이후 이벤트 시퀀스가 error_event로 끝났다면 그 턴은 실패이므로 완료로 저장하면 안 됩니다.

메타데이터(stop_reason, usage, 도구 호출)가 필요하면 텍스트만 모으지 말고 SDK 스트리밍 헬퍼의 최종 메시지 집계 메서드를 사용합니다.

배압(backpressure)

느린 소비자에게 스트리밍할 때 생산자가 제한 없이 읽으면 메모리가 계속 늘어납니다. 상한이 있는 큐를 두고, 가득 차면 읽기를 일시 정지하거나 스트림을 취소합니다.

재시도와 중복

중단된 스트림은 마지막 바이트부터 재개할 수 없습니다. 재시도는 새 요청이며, 같은 작업이 두 번 기록되지 않도록 멱등성 키나 작업 식별자를 씁니다.

CHAPTER 05

컨텍스트 관리

장시간 실행 에이전트 문제의 단골 주제입니다. "더하지 말고 덜어낸다"가 일관된 정답 방향입니다.

증상과 원인

응답의 초점이 흐려지거나 낡은 정보를 인용한다면, 원인은 거의 항상 무의미해진 정보가 컨텍스트에 남아 현재 근거와 경쟁하고 있는 것입니다. 모델에게 "무시하라"고 요청해서는 해결되지 않습니다.

세 가지 도구

  • 가지치기(prune) — 해결된 도구 결과, 중단된 분기, 낡은 로그를 제거합니다
  • 압축(compact) — 남은 이력을 요약합니다. 요약은 손실이 있는 변환이므로 무엇을 반드시 남길지 지시하고, 이후 연속성을 검증합니다
  • 외부 저장 — 정확해야 하는 값(부품 번호, 식별자, 검증된 사실)은 요약에 맡기지 말고 구조화된 애플리케이션 상태나 외부 저장소에 두고 필요할 때 조회합니다

서브에이전트 격리

대용량 원본을 다루는 조사 작업은 서브에이전트가 자기 컨텍스트에서 수행하고, 부모에게는 간결한 결론만 반환합니다. 여러 대상을 조사한다면 대상마다 별도 컨텍스트를 써서 서로 섞이지 않게 합니다.

검색 기반 접근

큰 저장소를 미리 전부 적재하지 말고, 질문이 도착한 뒤 관련 섹션만 조회해 넣습니다. 이때 출처 식별자를 함께 넣어야 답변에서 인용할 수 있습니다.

세션 분리

섞이면 안 되는 작업 단위(고객 계정, 조사 건, 브라우저 탭)는 대화 상태 자체를 분리합니다. 프롬프트에 이름표를 붙여 모델이 구분하게 하는 것은 격리가 아닙니다.

Claude Code에서는 /clear(무관한 작업으로 전환), /compact(같은 작업 계속), resume(중단한 작업 재개)을 상황에 맞게 구분해 씁니다.

반복되는 오답: "시스템 프롬프트로 옮기면 컨텍스트를 안 쓴다", "캐싱하면 컨텍스트가 늘어난다", "메시지를 나눠 담으면 총량이 준다" — 전부 틀렸습니다.

CHAPTER 06

비용과 성능 최적화

캐싱의 동작 원리와 측정 방법이 핵심입니다. 특히 캐시 접두부 규칙은 여러 번 나옵니다.

프롬프트 캐싱

캐시는 접두부(prefix) 단위로 동작하며, 바이트 단위로 완전히 동일할 때만 적중합니다. 중간에 무언가 바뀌면 그 지점 이후가 전부 무효화됩니다.

따라서 프롬프트 구성 순서가 곧 캐시 성능입니다. 안정적인 것(시스템 지시, 도구 정의, 정책 문서)은 앞에, 매번 바뀌는 것(타임스탬프, 사용자별 데이터)은 뒤에. 캐시 중단점은 변화 지점 앞에 둡니다.

적중 여부는 추측하지 말고 usage의 캐시 읽기 토큰으로 확인합니다.

위험한 오답: "요청마다 고유 ID를 앞에 넣는다"(캐시 완전 무력화), "고객 정보까지 캐시해 재사용한다"(데이터 유출), "캐시 쓰기 후에는 도구 정의를 생략해도 된다"(사실이 아님).

Message Batches

즉각적인 응답이 필요 없는 워크로드는 배치로 제출하면 상당한 할인을 받습니다. 캐싱과 함께 쓸 수 있습니다.

배치는 결과 순서를 보장하지 않으므로 요청마다 안정적인 custom_id를 부여하고 원본과의 관계를 제출 전에 저장합니다. 일부만 실패하면 실패한 것만 새 배치로 묶습니다.

Files API

크고 자주 바뀌지 않는 문서를 반복 사용한다면 한 번 업로드하고 파일 참조로 재사용합니다. PDF 콘텐츠 블록으로 참조하면 텍스트와 페이지 이미지가 함께 전달됩니다.

단, Files API는 파일을 저장하는 기능입니다. Zero Data Retention 같은 보관 요구가 있다면 인라인 전송을 택하고, 기능별 보관 정책을 개별로 확인해야 합니다.

모델·노력 라우팅

작업 성격이 다르면 나눕니다. 대량·단순 작업은 저렴한 등급이나 낮은 노력(effort)으로, 소수의 어려운 작업은 강력한 등급이나 높은 노력으로 라우팅합니다.

  • 라우팅 기준은 트래픽 양이 아니라 난이도입니다
  • 상향 조정은 감이 아니라 평가 근거로 결정합니다
  • 경로별로 따로 평가합니다. 합쳐서 평균 내면 소수의 어려운 작업 품질 저하가 묻힙니다
  • 모델 계열을 바꾸기 전에 같은 모델의 노력 설정 조정부터 시도할 수 있습니다

비용 측정

요청 건수나 문자 수 추정으로는 실제 비용을 설명할 수 없습니다. usage 필드를 범주별로 분해해야 합니다.

  • 입력 토큰 / 출력 토큰
  • 캐시 쓰기 / 캐시 읽기 — 요율이 다르므로 반드시 분리
  • 워크로드별 집계 후 문서화된 가격 적용
CHAPTER 07

프롬프트 엔지니어링

"프롬프트를 더 강하게 쓴다"는 거의 항상 오답입니다. 구조와 측정이 정답 방향입니다.

롱 컨텍스트 배치

긴 자료는 앞에, 질문과 지시는 뒤에 둡니다. 그리고 각 문서를 구분자(XML 태그 등)로 감싸 경계를 명확히 합니다. 여러 출처를 비교한다면 각 문서에 안정적인 제목을 붙여야 답변에서 출처를 지목할 수 있습니다.

출력 형식이 흔들릴 때

지시를 늘리거나 강조어를 추가하지 말고 퓨샷 예시를 보여줍니다. 예시는 필드 구성, 값의 형식, 허용 범위를 한꺼번에 시연합니다. 특히 레이블 이름이 직관적이지 않거나 유사 범주가 혼동될 때, 혼동되는 범주에만 대표 예시를 넣는 것이 효과적입니다.

기계가 소비하는 출력이라면 구조화된 출력 스키마로 계약을 고정하고, 그 위에 비즈니스 규칙 검증을 한 겹 더 얹습니다.

모순된 지시

출력이 오락가락한다면 지시에 모순이 없는지 먼저 봅니다. "항상 간결하게"와 "실패마다 상세히"는 함께 성립할 수 없습니다. 명시적 우선순위와 조건부 동작으로 재작성해 모순을 제거하는 것이 첫 수정입니다.

측정 기반 개선

프롬프트 수정은 토론이 아니라 측정으로 끝냅니다.

  1. 실패하는 대표 사례를 수집하고 원하는 정답을 정의
  2. 한 번에 하나의 요소만 수정 (여러 개를 동시에 바꾸면 원인을 알 수 없음)
  3. 튜닝에 쓰지 않은 held-out 세트로 재평가
  4. 기준은 결과를 보기 전에 정해둠

오답 패턴: "더 긴 프롬프트를 고른다", "'필수'·'중요' 같은 강조어를 계속 추가한다", "실패할 때마다 모델을 바꾼다", "가장 어려운 사례 하나에 맞춘다".

자기 검토는 검토가 아니다

같은 대화에서 자기 답을 확인하게 하면 거의 항상 동의합니다. 별도의 검증 단계에서, 무엇을 찾을지 명시한 체크리스트(근거 없는 주장, 놓친 예외)로 검증해야 오류가 드러납니다.

추론 깊이가 부족할 때

프롬프트를 다듬어도 다단계 추론이 부족하다면 확장 사고(thinking) 모드를 검토합니다. 단 추론 토큰이 늘어 비용과 지연 시간이 증가하므로 품질 향상과 함께 비교 측정해야 합니다. thinking 모드는 일부 파라미터(커스텀 temperature, 강제 tool_choice)와 함께 쓸 수 없다는 호환성 제약도 기억해 두세요.

CHAPTER 08

보안과 프라이버시

출제 비중이 가장 높은 영역 중 하나입니다. 정답 방향이 일정해서 패턴만 익히면 확실히 맞출 수 있습니다.

프롬프트 인젝션 방어의 두 축

외부에서 가져온 콘텐츠(웹페이지, 이슈, 이메일, 문서)에 악의적 지시가 숨어 있을 수 있습니다. 방어는 항상 두 층입니다.

  1. 신뢰 경계를 구조로 세운다 — 신뢰하는 규칙은 system에, 신뢰할 수 없는 입력은 user 콘텐츠에 구분 표시된 데이터로. 그리고 "이 영역의 내용은 지시가 아니라 데이터"라고 명시합니다
  2. 중대한 동작 앞에 모델 밖의 관문을 둔다 — 결제, 취소, 삭제, 머지, 정보 공개 같은 되돌리기 어려운 동작은 결정론적 인가 + 사람 승인을 통과해야만 실행되게 합니다

두 번째가 특히 중요합니다. 모델은 결국 설득당할 수 있으므로 최종 방어선은 반드시 모델 바깥에 있어야 합니다.

오답 패턴: "더 큰 모델을 쓰면 막힌다", "temperature를 조정한다", "페이지 텍스트를 시스템 프롬프트로 옮긴다", "숨겨진 지시가 있는지 모델에게 물어본다", "콘텐츠가 스스로 신뢰성을 선언하게 한다" — 전부 오답입니다.

인증과 인가

스키마 검증은 형태만 확인합니다. "이 사용자가 이 주문의 소유자인가" 같은 질문은 스키마가 답할 수 없으므로 애플리케이션 코드에서 인가를 검증해야 합니다.

  • 인가 판단을 모델에게 맡기지 않습니다 — 표현이나 확신 정도로 권한을 판단할 수 없습니다
  • 인증(누구인가)과 인가(무엇이 허용되는가)는 별개입니다. 401 vs 403
  • 도구를 노출하거나 실행하기 전에 검증합니다

자격 증명

클라이언트에 배포된 비밀은 비밀이 아닙니다. 난독화·분할·암호화 모두 시간을 조금 벌 뿐입니다. 요청을 신뢰할 수 있는 서버로 옮기고 키는 관리형 시크릿 저장소에 둡니다. 노출된 키는 즉시 폐기하고 교체합니다.

멀티테넌트 환경이라면 공유·장수명·광범위 토큰 대신 사용자별로 범위가 한정된 단수명 자격 증명을 발급하고, 민감한 도구 실행 시 신원을 다시 검증합니다.

데이터 최소화

가장 강력한 프라이버시 통제는 애초에 보내지 않는 것입니다. 순서대로 겹쳐 쌓습니다.

  1. 작업에 필요 없는 필드 제거, 식별자 마스킹 (숨겨진 메타데이터도 전처리로 제거)
  2. 조회 전 인가와 테넌트 격리 강제 — 허용된 레코드만
  3. 저장된 데이터에 역할 기반 접근 제어
  4. 보관 및 삭제 정책 — 무기한 보관은 위험을 키웁니다

함정: "모델에게 개인정보를 언급하지 말라고 요청한다"(데이터는 이미 전송됨), "이름만 지우면 익명"(재식별 위험), "보관 기간이 길수록 안전"(정반대), "암호화해서 보내면 된다"(분석하려면 복호화 필요).

샌드박스와 네트워크

코드 실행 환경에서는 이그레스를 기본 차단하고 승인된 패키지 출처만 허용 목록으로 엽니다. 자격 증명은 실행 환경 바깥에 둡니다.

CHAPTER 09

에이전트 설계

"워크플로냐 에이전트냐"는 거의 모든 세트에 나옵니다. 판단 기준 하나만 확실히 잡으면 됩니다.

가장 중요한 판단 기준

단계가 미리 알려져 있고 고정되어 있다면 그것은 워크플로입니다. 에이전트는 경로를 미리 알 수 없을 때 쓰는 도구입니다.

예측 가능한 실행 경로, 제한된 비용, 감사 가능한 체크포인트를 요구한다면 그것은 모두 결정론적 코드가 제공하는 성질입니다. 모델은 진짜 판단이 필요한 지점 한 곳에만 좁게 투입합니다.

둘을 함께 쓰기

실제 시험 문제는 대부분 혼합을 답으로 요구합니다.

  • 필수 검사·승인은 결정론적 워크플로 단계로 고정 — 모델이 건너뛸 수 없게
  • 개방형 조사 구간만 범위가 한정된 에이전트에 위임 — 승인된 도구만, 고정된 한도 안에서
  • 에이전트의 결과는 다시 결정론적 결정 흐름으로 반환 — 최종 판단은 코드가

주요 패턴

  • 오케스트레이터-워커 — 독립적인 하위 작업을 병렬로 위임하고, 간결한 결과만 모아 종합. 격리와 지연 시간 개선을 동시에 얻습니다
  • 라우팅 — 요청을 정의된 범주로 분류한 뒤 해당 전문가의 도구만 가진 경로로 보냄
  • 평가자-최적화자 — 제안 → 실행 → 별도의 평가 단계가 구체적 결함 반환 → 수정 → 재평가
  • 사람 개입(human-in-the-loop) — 되돌릴 수 없는 동작 앞에서 일시 정지하고 승인을 기다림. 세션을 유지하고 응답 후 같은 세션에서 재개
  • 상태 그래프 — 지속 상태, 명시적 전이, 재개 가능한 승인, 분기 시각화가 필요할 때

실행 순서 판단

  • 서로 독립적이면 병렬 — 지연 시간이 가장 느린 하나로 줄어듭니다
  • 다음 단계가 모든 결과를 필요로 하면 그 지점에서만 기다림(배리어)
  • 각 단계가 이전 단계의 정확한 출력에 의존하면 순차, 그리고 구조화된 결과로 전달

루프 제어

에이전트 루프에는 항상 상한을 둡니다. 최대 턴 수나 도구 호출 예산을 정하고, 초과하면 조용히 멈추지 말고 통제된 최종 오류로 종료해 상위 시스템이 인지하게 합니다.

공유 상태

여러 에이전트가 같은 산출물을 직접 편집하게 하지 않습니다. 조정자가 범위를 나눠 할당하고, 에이전트는 구조화된 권고만 제출하며, 적용은 한 곳에서 순차적으로 이루어져야 일관성과 복구 가능성이 확보됩니다.

반복되는 오답: "자율 에이전트가 필요한 검사를 스스로 판단", "에이전트가 자기 결정을 승인", "여러 에이전트가 경쟁해 가장 빠른 결과 채택", "상세한 프롬프트로 순서를 지시".

  • PreToolUse — 실행 전 검사와 차단. 파괴적 동작, 시크릿 기록 방지에 사용
  • PostToolUse — 실행 후 검증과 후처리. 포매터·스캐너 실행 후 결과를 루프로 반환

훅에서 차단하려면 명시적인 deny 결정을 반환해야 합니다. 로그만 남기고 빈 객체를 반환하면 도구는 그대로 실행됩니다. 그리고 차단 시 구체적인 사유를 돌려줘야 모델이 같은 시도를 반복하지 않습니다.

여러 클라우드 제공자

제공자마다 모델 식별자 형식과 지원 기능이 다릅니다. 하나의 식별자를 공유하지 말고 제공자별 매핑과 기능 확인을 유지하며, 배포 전에 각각 검증합니다. 자동 페일오버 시 데이터 소재지 확인은 필수입니다.

CHAPTER 11

운영과 릴리스

정답 패턴이 가장 일정한 영역입니다. "버전 고정 → 평가 → 단계적 배포 → 롤백"만 기억하면 됩니다.

구성 버전 관리

"latest", "default", 이동형 모델 별칭은 재현 가능한 구성이 아닙니다. 시간에 따라 가리키는 대상이 바뀌므로 나중에 "그때 무엇이 돌아갔는가"에 답할 수 없습니다.

프롬프트를 코드처럼 다룹니다. 프롬프트·모델 식별자·도구 스키마·평가 세트를 함께 버전 관리하고, 불변 버전 + 가변 릴리스 포인터 구조로 두면 재현성과 즉시 롤백을 동시에 얻습니다. 모든 운영 응답에 어떤 구성이 쓰였는지 기록합니다.

릴리스 절차

  1. 기준선 확보 — 현재 구성의 성능을 먼저 측정 (비교 기준)
  2. 후보 버전 고정 후 평가 — 기존 평가 세트를 그대로 돌려 나란히 비교. 품질뿐 아니라 지연 시간과 비용도
  3. 단계적 배포 — 소규모 집단 또는 카나리로 노출 제한, 사전에 정의된 롤백 임계값과 함께
  4. 모니터링 후 확대 — 기준을 충족할 때만
  5. 테스트된 롤백 경로 유지 — 문서화만이 아니라 실제로 검증된

한 번에 여러 변수를 바꾸지 않습니다. 모델·프롬프트·파서를 동시에 바꾸면 회귀 원인을 영영 특정할 수 없습니다.

평가의 원칙

  • 일반 벤치마크는 내 작업의 성능이 아닙니다. 작업별 평가가 필요합니다
  • 평균이 아니라 구간별로 봅니다. 안전에 치명적인 실패가 작은 구간에 집중되면 평균은 안전의 근거가 되지 못합니다
  • 확률적 시스템이므로 여러 번 실행한 분포로 평가합니다
  • 기준은 결과를 보기 전에 정합니다

오류 처리

재시도는 지수 백오프 + 지터 + 상한이 한 세트입니다. 재시도 전에 항상 "이 오류가 재시도로 해결될 수 있는가"를 먼저 묻습니다.

상태를 바꾸는 작업의 재시도에는 멱등성 키가 필요합니다. 응답 유실은 미실행을 뜻하지 않습니다.

도구 결과의 실패 처리

실패했는데 성공처럼 보이는 결과를 반환하는 것이 가장 위험합니다. 구조화된 오류 결과로 실패 범주(재시도 가능/불가)와 안전한 세부 정보를 담아 돌려주고, 허용된 복구 경로를 고르게 합니다.

폐기(deprecation)

목록화 → 일정 공표 → 호환 어댑터로 점진 이전 → 사용량 0 확인 → 삭제. 장애를 발견 수단으로 쓰지 않습니다.

CHAPTER 12

요구사항과 소프트웨어 공학

코드나 API가 아닌 문제도 매 세트에 나옵니다. 기준이 단순하니 놓치지 마세요.

기능 vs 비기능

시스템이 무엇을 하는가 → 기능 요구사항. 얼마나 잘·안전하게·빠르게·안정적으로 하는가 → 비기능 요구사항.

  • 기능 — 티켓 분류, 문서 요약, 필드 추출, 예약 식별자 반환
  • 비기능 — 지연 시간, 가용성, 리전 장애 내성, 테넌트 격리, 처리량

이 구분이 중요한 이유는 검증 방법과 담당 팀이 다르기 때문입니다. 정확도는 평가 세트로, 격리는 보안 테스트로, 리전 복구는 장애 주입으로, 지연 시간은 부하 테스트로 검증합니다.

측정 가능한 요구사항

"정확하고 빠르게"에는 측정할 것이 없습니다. 형용사에 숫자와 조건을 붙여야 요구사항이 됩니다.

  • 정확도 → 레이블이 달린 평가 세트 + 필드 수준 채점 + 최소 임계값 + 대표적인 입력 조건
  • 지연 시간 → 백분위수(p95 등) + 부하 조건 + 측정 구간
  • 애매한 입력 → 저신뢰·판독 불가 증거를 어떻게 처리할지도 정의
  • 출력 → 필수 필드와 근거 참조까지 명시

순서에 주의: 요구사항 → 아키텍처 → 모델 선택입니다. 모델을 먼저 고르고 그 성능에 요구사항을 맞추면 목표가 현재 상태로 고정됩니다.

변경 관리

  • 큰 리팩터는 동작을 보존하는 작은 변경으로 쪼개고, 경계마다 테스트를 두고, 점진적으로 머지
  • 공유 인터페이스 교체는 호환 어댑터 + 계약 테스트로 공존시키고 하나씩 이전
  • 중복된 로직은 버전 관리되는 공유 계층으로 모으고 계약과 테스트로 고정
  • AI가 만든 변경이라고 검토 기준이 낮아지지 않습니다. 오히려 사람이 읽을 수 있는 크기로 나누는 일이 더 중요해집니다

근거의 형태

조용히 깨질 수 있는 변경일수록 회귀 테스트가 유일한 방어선입니다. 분기가 N개면 근거도 N개의 케이스로. 스크린샷 한 장, "코드가 깔끔해 보인다", 사후 모니터링만으로는 부족합니다.

의존성과 배포 재현성

플러그인·의존성은 버전을 고정하고 조합을 테스트하며 승인된 것만 올립니다. 로컬과 CI가 다르게 동작한다면 설정과 잠금 파일을 저장소에 넣고 CI가 검증 후 설치하게 합니다.

서드파티 확장은 소스·게시자·요청 권한·의존성·버전을 검토하고 격리된 환경에서 먼저 실행한 뒤 승인 기록을 남깁니다. 훅과 MCP 설정은 슬래시 명령보다 오히려 더 위험하므로 반드시 함께 검토합니다.

CHAPTER 13

시험 직전 체크리스트

선택지를 보는 순간 걸러낼 수 있는 패턴들입니다. 네 세트 211문제에서 반복적으로 확인된 것만 모았습니다.

거의 항상 오답인 서술

  • "모델이 알아서 기억할 것이다" — 세션 간 자동 메모리는 없습니다
  • "API가 자동으로 차감/조정/보정해 준다" — 하지 않습니다
  • "프롬프트로 요청하면 지켜진다" — 지시는 강제가 아닙니다
  • "사용자 신고나 사후 리포트로 발견한다" — 사용자를 탐지 수단으로 쓰는 것
  • "더 큰 모델이면 해결된다" — 보안·통제 문제에서는 특히 아닙니다
  • "스키마를 통과했으니 값도 맞다" — 형태와 의미는 별개입니다
  • "확신에 차 있으니 맞다", "길게 설명했으니 맞다" — 어조와 길이는 정확성의 지표가 아닙니다
  • "로그를 남긴다" (통제 대신) — 로그는 차단이 아닙니다
  • "무기한 보관하면 안전하다" — 정반대입니다
  • "모두 무시하라고 지시한다" — 컨텍스트에 있으면 영향을 줍니다

거의 항상 정답인 방향

  • 통제는 모델 밖에, 되돌릴 수 없는 동작 앞에
  • 검증은 두 겹: 구조(스키마) + 의미(비즈니스 규칙)
  • 변경은 한 번에 하나씩, 버전을 남기고, 되돌릴 길을 두고
  • 컨텍스트는 더하지 말고 덜어내기
  • 단계가 고정이면 워크플로, 모를 때만 에이전트
  • 데이터는 최소한만 보내고 필요한 만큼만 남기기
  • 추측하지 말고 측정하기 (usage, 토큰 계산, 평가 세트)
  • 독립적인 것은 병렬, 의존하는 것은 순차

복수 정답 문제 요령

"두 가지를 고르세요"인 경우, 대개 서로 다른 층의 조치가 짝을 이룹니다. 같은 성격의 조치 두 개보다는 입구와 출구, 예방과 검출, 구조와 검증처럼 보완 관계인 조합을 찾으세요.

예: 인젝션 방어 = 신뢰 경계(구조) + 실행 관문(통제) / 요구사항 명확화 = 기능 기준 + 운영 기준 / 배치 처리 = 식별자 매핑 + 실패만 재시도.

문제 읽는 순서

  1. 요구사항 문장에 밑줄 — "반드시", "~하지 않으면서", "~전에" 같은 제약이 답을 결정합니다
  2. 선택지 안의 자기 고백 찾기 — "~하지 않는다", "~를 확인하지 않고", "~는 남지 않는다"라고 스스로 말하는 선택지는 대개 오답입니다
  3. 코드가 있으면 코드부터 — max_tokens: 120, count?, default: undefined 처럼 결함이 눈에 보이는 경우가 많습니다
